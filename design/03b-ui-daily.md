## 3. 信息架构与 UI（续 · §3.4–§3.13）

### 3.4 胖乖生活页

1. 未登录 → 手机验证码或粘贴 Token  
2. 已登录 → 历史设备列表（最近用过的饮水机）  
3. 大按钮「开水」；可选积分抵扣开关  
4. 成功 → 页面提示卡 + 本地记一笔订单快照  
5. 底部：余额、历史订单（分页或简单列表）

**开水设置**（2026-09-20 起并入开水页，`SubpageScreen.WATER_SETTINGS` 已删除）：
两项都是今日页开水卡的行为——**显示开水卡片**（默认开，关掉今日页不再展示含未登录态）+
**点击方式**（单击/双击，2026-09-23 起只对开水页大按钮生效；今日页余额面板的开水按钮
固定单击——点余额→弹窗→点开水已是明确意图链，不再需要防误触确认）。
2026-09-19 曾收进独立「开水设置」子页，2026-09-20 并入开水页尾部（登录/未登录两态共用同一区块），
不再单独成页。均不依赖登录态——未登录也能关卡片显示与调点击方式；登录/退出在页内完成。
「我的」侧入口名「胖乖生活」（2026-09-26 统一：账号卡三格、扩展服务入口、引导第 4 步、
登录失效通知、页标题同一口径；此前为「胖乖生活一键开水」，「开水」作为动作词仍用于
卡片、按钮与流程文案）。

**提示出口（2026-09-19）**：登录/验证码/出水超时/登录失效/查询失败等一次性结果走页面
`AppSnackbarHost`（语气随结果：失败=错误、超时与失效=警告、登录成功=成功），
不再用系统 Toast。今日页开水卡的相同事件也由**今日页**收集展示——
此前只有开水页收事件流（今日页点「开水」后的超时/失效提示全部静默丢弃，Channel 无人消费）。

**登录态是共享的，退出要二次确认（2026-09-27）**：登录态的唯一来源是
`QiekjRepository.loggedIn`（进程级 `StateFlow`，`saveToken` / `logout` 就地翻转）。
今日页开水卡与开水页各持一份 `WaterViewModel`，两个实例共用的只有仓库单例——
在开水页登录或退出，卡上的登录形态、余额与设备跟着这条流走，不用下拉、也不用重启应用
（此前只在 VM 初始化时读一次 token，登录后卡片一直停在未登录）。顶栏退出图标加
**二次确认**：清 Token 顺带清开水订单快照，重新登录要再收一次短信，误触代价不对等。

**充值 · 下拉刷新 · 登录手机号（2026-09-28）**：

- 余额行加「充值」按钮，深链到支付宝的胖乖生活小程序充值页（`ui/water/QiekjRecharge`，
  链路拆解见 §6 P6 追加）。胖乖的 REST 没有充值端点，充值不在本 App 内完成；
  未装支付宝时走页面 snackbar 提示，返回本页（ON_RESUME）自动重拉余额。小注里
  「核对小程序账号与本 App 登录手机号一致」那句是用户要求加的（小程序按支付宝
  登录态进账号，可能不是本 App 的账号），别删。
- 刷新改**整页下拉**（`PullToRefreshBox`，与趣智页 / 消费流水页同一套；
  `WaterViewModel.refresh()` 等余额、设备两轮 join 完才收指示器），余额行原来的
  刷新按钮删除。`refreshing` 只归下拉刷新，进页首载与登录路径仍直调
  refreshBalance / refreshDevices，别拿它当一般 loading。
- 余额行下显示**登录手机号**：取自仓库记住的手机号（短信登录落盘、Token 登录沿用
  旧值、没有就不显示），默认遮蔽（复用 `QzxyPhoneMask`，名字带 Qzxy 但是通用工具）
  点眼睛才展开——与趣智账号行 / 「我的」页学号同口径；与登录输入框的值是两回事。
- 顶栏加**复制 Token**（已登录时显示，图标在「退出登录」左边）：token 是账号通行证，
  复制给另一台设备的「Token 登录」粘贴（换机不用再收短信），提示语按凭据口径写
  「只粘到本应用的『Token 登录』，别发到别处」（与趣智调试页「复制会话串」同款）。

### 3.5 作息表（2026-09-17 实测，唯一准绳）

学校作息：**每小节 40 分钟**；大节内两小节之间休息 **5 分钟**；大节之间换教室 **20 分钟**
（上午一二节→三四节、下午五六节→七八节）。
11:40→14:00 是 140 分钟午休、17:10→19:00 是 110 分钟晚饭，不属于「换教室」。
5 个大节共 **11 小节**（第 5 个大节是 9/10/11 三小节，与教务页行标签「第九十十一节」及 19:00~21:10 对齐）。

| 节 | 起止 | 节 | 起止 | 节 | 起止 |
|----|------|----|------|----|------|
| 1 | 08:30–09:10 | 5 | 14:00–14:40 | 9 | 19:00–19:40 |
| 2 | 09:15–09:55 | 6 | 14:45–15:25 | 10 | 19:45–20:25 |
| 3 | 10:15–10:55 | 7 | 15:45–16:25 | 11 | 20:30–21:10 |
| 4 | 11:00–11:40 | 8 | 16:30–17:10 | | |

校验方式：用「40 分钟 + 5 分钟」逐节递推，5 个大节的结束时间（09:55 / 11:40 / 15:25 / 17:10 / 21:10）
与教务页 `xskb_list.do` 行标签给的时间逐一吻合。

**`TimeSlot` 存小节（11 条），`Course.startSection/endSection` 也是小节号**，两者语义一致，不再做折算。
`DefaultData.defaultTimeSlots` 就是上表。作息变更走「我的 → 课表设置 → 作息表」，届时以用户值为准：
保存时写 `time_slots` 并把 DataStore 的 `slot_customized` 置位，此后 `migrateTimeSlotSchema` 直接跳过，
避免下一次结构性迁移把用户改过的作息悄悄改回默认值。「恢复默认作息」会清掉该标记，重新交回迁移管辖。

### 3.6 桌面小组件（2026-09-18，P6；2026-09-20 单条目自适应；2026-09-27 二条目改版；2026-09-28 开水两卡）

入口：**我的 → 桌面小组件**（独立二级页，`SubpageScreen.WIDGET_SETTINGS`）。

#### 二条目（课表 + 校园卡 · 电费，2026-09-27）

选择器里两条**内容**条目，各自独立 receiver（`ScheduleWidgetReceiver` /
`CampusCardWidgetReceiver` + 各自 provider XML）。**按内容拆不等于按尺寸拆**——「不要
按尺寸拆 receiver」的老规矩指尺寸变体，不变。当天曾按内容拆成三条（课表 / 校园卡 /
电费），落地后发现 2 格宽的卡片（真机实测 150×178dp）只放得下一块信息、桌面看着空，
当天合并回一条「校园卡 · 电费」：

| 条目 | 默认格位 | 显示 | 点击 |
|------|---------|------|------|
| 水贝贝 · 课表 | 4×2 | 尺寸自适应三档（见下） | 今日页；网格区→课表页 |
| 水贝贝 · 校园卡 · 电费 | 4×2（可拖 2×2） | 主区：正式卡余额大字 + 更新时刻；副行：寝室电费（度数 · 折合金额） | 整卡 → 付款码页（未开凭证 → 校园卡设置页）；**电费副行 → 缴费账单·用电统计** |

合并卡的四条口径：

- **副行让给电费，电子账户余额不再上卡片**：账户余额在付款码页与生活页都能看。快照
  合成一个 `LifeCardSnapshot`（campus + power），后台一次刷新（写状态 + `update()`）
  把两份数据一起推上桌面；
- **点击分区**靠 Glance 的 `PendingIntent` 覆盖——子元素的 clickable 盖住整卡那层，
  与课表条目的周网格区同一手法；副行外面套 `Box` 垫到 23dp 高，手指点得准；
- **副行文案分档**（`LifeWidgetFormat.powerLineText`）：宽档 `寝室电费 23.7 度 ·
  折合 ¥14.71（0.62 元/度）`，窄档压成 `电费 23.7 度 · ¥14.71`（放不下「寝室」「折合」
  与单价括号）；无读数给 `寝室电费 · 暂无读数`，缺单价只报度数（**不猜**）；
- **两条数据的红线各自不变**：校园卡 2 小时闸门 + 失败不重试不落时刻、电费零网络，
  详见下面两条 bullet。

- **点击路由**：复用 `widgetIntent`（`NEW_TASK|CLEAR_TASK`）+ `EXTRA_ROUTE` 新增
  `pay_code` / `power_bill` / `campus_card` 三个值（`MainActivity` 常量），消费后起
  `SubpageActivity`——保持「点小组件 = 从主窗口重新开始」的既有语义，不直接起二级页。
- **校园卡数据与刷新**：权威快照在 DataStore（`life_widget_prefs`：cardFen /
  fetchedAtMs / hideBalance），Glance 状态只是渲染镜像（新添加的实例首帧就有上次已知值）。
  口径 = **正式卡余额**（与余额提醒一致，不含电子账户）。取数时机：
  App 内成功取余额顺手推（付款码页 / 生活页 / 余额提醒日检，数据在手上零额外请求）+
  15 分钟兜底 tick 过 **2 小时闸门**（`CampusBalanceGate`，纯函数；时钟回拨视为该取）。
  **失败不重试、不落时刻**（与余额提醒同口径，防撞风控）；验证码接口（8002/8003）
  在这条链路上绝不触碰。**码不预取**：小组件只是启动器，出码 / `FLAG_SECURE` /
  亮度 / 扫码自动退出仍只在付款码页（§3.10「只有一处出码」原样保留）。
- **电费数据与刷新（零网络红线）**：任何刷新路径都不发网络请求。数据 = Room
  `power_readings` 最新一条的本地镜像（`LifeWidgetSync.refreshLifeWidgets`），由
  生活页刷新 / 缴费账单页刷新 / 充值 / 余额提醒日检成功后顺手推 + 15 分钟 tick 本地
  兜底；读数唯一写入处仍是 `PowerRepository.snapshot()`，**读数密度 = 打开 App 的
  密度**（§3.13 既有红线），小组件不许变相轮询第三方平台。折合金额走
  `BalanceAlert.remainingYuan` 唯一换算处，单价缺失只报度数（**不猜**）。
- **窄档排版（2026-09-27，真机实测）**：桌面格位不是正方形——同一台机（Redmi K70 /
  澎湃OS，density 420）上 2 格宽的小组件只有 150dp，2 格高却有 178dp，4 格宽 344dp，
  所以 2×2 看着比宽高。外框比例由 launcher 网格决定，App 改不了；能改的是卡片内排版：
  实测宽度 < 200dp（`isNarrowWidth`，`ui/widget/LifeWidgetUi.kt`）时三处间隔都拿弹性
  （`WidgetGap`），剩余高度三等分 → 内容铺满卡片。当天先试过「整块居中」，上下各留
  一大段空白，被用户第二次否掉后改成均分。宽档（4×2）给固定间距 + 末段弹性，
  保持「头部贴顶 + 大字 + 按钮沉底」。
- **隐私**：「在小组件中隐藏余额」开关（设置页校园卡节内，默认关，与余额提醒通知的
  明示口径一致）：隐藏后主区显示 ¥ ••••，点击仍可出示付款码；电费副行照常显示。
  凭证关闭时主区回落引导文案（「一关了之」口径），副行按无读数处理，不残留旧数字。
- 空态：主区 =「余额待更新 / 未开启校园卡凭证」，副行 =「寝室电费 · 暂无读数」，
  都给一句能照着做的引导；「近 7 日日均」为后续可加项（需与账单页同口径接 `PowerUsage`，
  2026-09-27 未实现）。

#### 开水两卡（胖乖开水 + 趣智开水，固定 2×2，2026-09-28）

选择器里再加两条**内容**条目：胖乖开水（`QiekjWaterWidgetReceiver` +
`widget_water_qiekj.xml`）与趣智开水（`QzxyWaterWidgetReceiver` +
`widget_water_qzxy.xml`）。两张卡都**固定 2×2**（provider XML
`resizeMode="none"`，用户要求不给拖动；真机 2 格实测约 150×178dp，天然落在
窄档排版），机制仍是单条目 + `SizeMode.Exact`，Glance 两条硬约束原样适用。

| 条目 | 格位 | 显示 | 点击 |
|------|------|------|------|
| 水贝贝 · 胖乖开水 | 固定 2×2 | 主区：小票余额大字（能付水钱的那个）+ 副行「小票 · 积分 N」 | 胶囊「去开水」→ 开水页并**自动开水**；整卡其余位置 → 只进开水页 |
| 水贝贝 · 趣智开水 | 固定 2×2 | 主区：余额大字；**用水中时整卡切成「用水中」大字 + 设备 · 已 N 分钟副行**；空闲副行给上次设备名 | 胶囊「去开水」→ 趣智页并**自动开阀**；整卡其余位置 → 只进趣智页 |

口径（编排层唯一入口 `WaterWidgetSync`，`ui/widget/WaterWidgetSync.kt`；快照模型
与文案在 `WaterWidgetModels.kt`，单测钉死）：

- **权威快照在 DataStore**（`water_widget_prefs`），Glance 状态只是渲染镜像，与合并卡
  同一套；登录态不落盘，构建快照时现算（胖乖 token / 趣智会话是唯一真相源）；
- **渲染路径零网络**。胖乖余额推送点 = 开水页 / 今日页开水卡 `refreshBalance` 成功
  （数据在手上零额外请求）+ 2 小时闸门（复用 `CampusBalanceGate`——名字带 Campus 是
  历史沿革，语义 = 小组件余额类取数的「距上次成功 ≥2 小时」闸门；失败不重试不落时刻，
  与校园卡同口径）；趣智余额推送点 = 趣智页 / 今日页卡片 `refreshAccount` 成功 + 同款
  2 小时闸门（只调 `balance()`，不带学校名查询）；
- **「用水中」是本地记账镜像**（Room 之外的 `QzxyWateringStore`，零网络）：开阀 /
  结算 / 手动标记 / 过期清理时即时推送（`QzxyViewModel.pushWaterWidget`）；超过
  1 小时未结算视为残留不上桌面（与趣智页 `applyWatering` 同一条过期规则）；
- **登录态翻转即时上卡**：两边 ViewModel 的登录态分支各推一次，桌面立即切
  「未登录」引导态；后台闸门取数遇到会话失效只当失败，**不代用户登出**；
- **胶囊直达开水（2026-09-28 用户拍板，替代当日早先的「阀不预开」）**：点「去开水」
  胶囊 = 进对应页面并**自动开水 / 开阀**；点卡片其余位置只进页面。实现三件套：
  ① route `water_start` / `qzxy_start` 与普通 `water` / `qzxy` 分开，前者在
  `MainActivity` 进页前武装一次性令牌 `WaterAutoStart`（`SubpageStack.kt`，进程内单槽、
  消费即清、**不进 `SubpageRequest`**——窗口链恢复重建页面时不得重触发开水）；
  ② `SubpageActivity` 在 composable 外消费令牌，传 `autoStart` 进页面首帧触发；
  ③ 动作全在页面 VM：`WaterViewModel.requestAutoUnlock`（等 init 的设备请求回来选
  「最近使用」那台，`devicesJob` 不重发；**绕过双击确认设置**——那颗开关只管页面里的
  大按钮，桌面胶囊是更明确的主动手势）与 `QzxyViewModel.requestAutoOpen`（设备口径同
  `openValveFromCard`：上次那台 → 唯一绑定那台；已在用水 / 流程进行中 / 未登录静默
  跳过）。未登录 / 无设备时页面自行引导或提示，直达不跳过登录表单。胶囊的
  `clickable` 盖住整卡那层（合并卡 PowerLine 同款 PendingIntent 覆盖）；
- 副行/时刻口径：时长按渲染时刻算，两次刷新之间不跳动（与课表卡「还有 N 分钟」同款）；
  趣智服务端余额全空时 `text` 退成 "-"，视为未取到（「余额待更新」），不把 `¥-` 渲染上桌面；
- 点击路由：`EXTRA_ROUTE` 开水相关共 `water` / `qzxy` / `water_start` / `qzxy_start`
  四个值，与付款码等同一套「先消费再启动」口径，落 `SubpageScreen.WATER` /
  `SubpageScreen.QZXY`。

#### 课表条目：一个条目，尺寸自适应

2026-09-20 改版（用户拍板）前是 **2×2 / 4×2 / 4×4 三个独立条目**，且三者都
`resizeMode="horizontal|vertical"`——用户拖动改大小后，几个条目落到同一形态，
选择器里三条内容相同，纯冗余。改版后选择器里只有**一个条目**：

| 条目 | 默认格位 | 可拖范围 | 内容随实测尺寸变 |
|------|---------|---------|-----------------|
| 水贝贝 · 课表 | 4×2 | 最小 2×2，最大 440dp（≈5×5） | 见下表「尺寸档」 |

尺寸在**运行时按实测 dp 分档**（`SizeMode.Exact`，量到什么算什么），不再吸附到
固定几档——拖动过程中内容跟着变，不会出现「2×2 和 4×2 显示一样」：

| 档 | 判定（实测 dp） | 内容 |
|----|---------------|------|
| `Compact` | 高度 < 170dp（2×2、4×2） | 日期行 + 焦点卡（正在上 / 下一节）。课名一行；**够宽时（≥200dp）副行「@地点 · 教师」与课名同排**，把宽度用起来（竖排需要 ~66dp，110dp 高的卡给不出）。今日上完时焦点位换成状态行 + 1–2 行单行式明日课程 |
| `List` | 高度 ≥ 170dp 且不够周网格（2×4、4×3 等） | 日期行 + 焦点卡（含进度条、课名两行、副行竖排）+ 剩余列表，**行数按高度算**（`WidgetMetrics.rowsBudget`），截断带「还有 N 节」 |
| `Week` | 宽高均 ≥ 230dp（4×4 及以上） | 日期行 + 摘要行 + **本周迷你网格** |

判据刻意**只看高度**决定是否降出 `Compact`：110×250 的竖条虽然窄，但高度足够
把列表铺开，按宽度判会让「拖高」这个动作什么都不变（旧版三档看起来一样的原因之一）。
阈值给宽、按「够不够放」判，不要求对齐整数格位——国产 ROM 给的实际尺寸不对齐格位。

#### 4×4 及以上：本周迷你网格

- 顶部摘要行（用户拍板保留）：正在上课 / 下一节一行（`正在上课 · 第3-4节 高数 @北B102`）；
  今天上完时显示「明天 10:15 高数 @北B102」
- 下方网格：左侧节次栏（1–11）+ 星期表头 + 课程块。列 = `ScheduleCalculator.visibleDays`
  （唯一来源，尊重显示设置的「显示周六 / 周日」；**不用 `day - 1` 当列号**）；
  行 = 小节号（1–11，与课表网格同一坐标）；块高 = 跨节数 × 行高。
  **按列排版（每天一列）而不是按行**：Glance 没有绝对定位也没有跨行合并，
  按行铺时一个跨节高块会把该列后续行整体推下去、与左侧节次栏错位
- 高亮规则：今天还有待上课程 → 高亮**今天**列；今天上完 / 今天没课 → 高亮**明天**列
  （回答「接下来」而不是「过去了」）
- 「现在」标记：`nowDay` 与 `nowSection` **必须同时命中**才给该格加淡色底
  （Glance 无 `offset`，逐格着色是唯一可行的时刻线表达）；只看节次号会把周一到周日
  整行点亮。今天上完 / 没课、或高亮列不可见（显示设置关了对应周末列）时不下发
- 同一列重叠的课只画最先开始的那门（widget 不做冲突排版）
- 块高放得下才画课名（7sp，跨两节及以上才写）；单节的 40 分钟课只留色块
- 点击：非网格区点击进 App **今日页**；**网格区点击进课表页**（`MainActivity` 读
  route extra 后切到课表 Tab；`SINGLE_TOP|CLEAR_TOP` 复用实例，`onNewIntent` 再消费）

#### 负一屏（澎湃OS / 小米）

**安卓原生小组件进不了小米负一屏**，这是平台限制，不是 App 的缺陷：

- 小米澎湃OS 官方文档（「小部件适配常见问题 Q&A」）明说「负一屏和桌面相互拖拽」是
  **「小米小部件」的专属能力**；「小米小部件」是在原生 AppWidget 之上按小米规范适配、
  上架「小部件中心」并经开放平台审核的产物。原生安卓组件只是「各家都支持展示，入口不一样」。
- 本 App 是原生 Glance 小组件，**不做小米小部件适配**（那是独立工程量 + 平台审核）。
- 设置页给两条替代路径：① 在负一屏右上角「+」搜索里试搜「水贝贝」，搜到即可添加；
  ② 打开「我的 → 日历同步」，课程进系统日历后由负一屏的**日历日程**系统卡片展示。

#### 刷新策略（三层兜底）

> 2026-09-19 实测定稿（两次推翻原方案后的终稿）。原方案「`provideGlance` 内每分钟 tick」
> **不可行**：Glance 的 `provideContent` 挂起到会话关闭（会话超时约 45 秒），且组合里没有
> `LaunchedEffect` / `rememberCoroutineScope`，无法自持定时循环。
> 第二版「后台算好快照写进状态、组合只读状态」也**不可行**，反编译 glance-appwidget 1.2.0
> 源码（`AppWidgetSession`）核实了两条硬约束：
>
> 1. 会话的 `LocalState` 只在组合开始时读一次 DataStore，且**先于 `provideGlance` 执行**——
>    `provideGlance` 里写状态，首帧读不到（表现为小组件永远停在空快照兜底页）；
> 2. `updateAppWidgetState` 只写 DataStore，**不推送 RemoteViews**——没有活跃会话时
>    光写状态桌面不会更新。

终稿数据流，两处都不许省：

1. **首帧**：`provideGlance` 里算快照（`computeAndStore`）→ 写状态 + **把快照直接捕获进组合**，
   `currentState` 空了退回首帧快照——首帧内容不依赖 DataStore 回读；
2. **后台刷新**（`refreshAll`）：算一次快照 → 逐实例「`updateAppWidgetState` 写状态 +
   `widget.update()`」两步。`update()` 对活跃会话推 `UpdateGlanceState` 事件（重读刚写的
   状态重组）；对已关闭的会话重跑 `provideGlance` 产出新 RemoteViews。

| 层 | 机制 | 作用 |
|----|------|------|
| 1 | **边界闹钟**：`AlarmManager.setAlarmClock` 排在「今天下一个上课/下课时刻」（2026-09-24 自 `setAndAllowWhileIdle` 改，真机非精确闹钟被 ROM 推迟几分钟） | 桌面真正需要变样子的只有这几个瞬间；触发后刷新并排下一个边界 |
| 2 | `WorkManager` 15 分钟周期兜底 | 进程被杀、闹钟被 ROM 推迟、跨天时仍会更新（周期下限就是 15 分钟） |
| 3 | 冷启动 + 课表数据变化主动刷 | 改完课表回桌面立即见到新内容 |

- 闹钟 2026-09-24 改用 `setAlarmClock`（系统级精确闹钟，到点即触发、不受 Doze/省电推迟，
  不需要任何特殊权限；与上课提醒同一手法）。此前的 `setAndAllowWhileIdle` 在 Redmi K70
  真机上被 ROM 省电策略推迟几分钟，用户报「上下课了小组件还不换」。代价仅是触发时
  状态栏短暂显示闹钟图标，对「课程到点」语义贴切。**别改回** `setAndAllowWhileIdle`。
- 今天没有剩余边界时，闹钟排到**次日 0:05**（跨天要换日期与列表）；
  闹钟落点已过期（设备刚唤醒/被延迟）时不顺延等待，直接触发立即刷（过去时刻的
  内容已经是旧快照，等多久都是错的）。
- **重启补排**（2026-09-24）：`ScheduleWidgetReceiver` 加收 `BOOT_COMPLETED`
  （RECEIVE_BOOT_COMPLETED 权限上课提醒已声明，不新增）→ `enqueueRefresh` →
  `refreshNow` 内部重排边界闹钟。此前重启后闹钟全丢，要等 15 分钟周期兜底拉起进程，
  期间小组件不按上下课时刻精确换。没有实例绑桌面时是廉价空跑。
- 无任何实例绑定桌面时，所有刷新入口都是空跑（`getGlanceIds` 为空直接 return）。
- `updatePeriodMillis="0"`（不用系统 30 分钟轮询）。
- 倒计时文案按「刷新时刻」计算，两次刷新之间不跳动——设置页说明里写明这一点。
- **两条目共用第 2 层**（2026-09-27）：`WidgetRefreshWorker` 在课表刷新之外追加
  `LifeWidgetSync.onPeriodicTick`——电费副行的本地镜像（零网络）+ 校园卡余额的
  2 小时闸门取数；边界闹钟只属课表条目（合并卡不随上下课变样）。冷启动侧
  `JuwApplication` 追加 `LifeWidgetSync.onColdStart`，口径相同。
- **开水两卡同样共用第 2 层**（2026-09-28）：`WidgetRefreshWorker` 再追加
  `WaterWidgetSync.onPeriodicTick`（本地镜像 + 胖乖 / 趣智余额 2 小时闸门），
  `JuwApplication` 追加 `WaterWidgetSync.onColdStart`；固定 2×2 不随上下课变样，
  边界闹钟与它们无关。无实例 / 未登录 / 闸门未到都是廉价空跑，内部各自吞错。

### 3.7 上课提醒（2026-09-19，P6）

入口：**我的 → 课表 → 上课提醒**（独立二级页，`SubpageScreen.REMINDER_SETTINGS`）。
默认关：通知是打扰型能力，用户显式开启；开启那一刻才请求 `POST_NOTIFICATIONS`（API 33+），
拒绝不阻塞开关本身（文案引导去系统设置再开）。调度与呈现对标 §3.6 的成熟链路，不另起炉灶。

#### 设置项（全局，DataStore）

| 项 | 值域 | 默认 |
|----|------|------|
| 上课提醒 | 开/关 | 关 |
| 提前量 | 5 / 10 / 15 / 20 / 30 分钟 | 10 分钟 |
| 作业截止提醒 | 开/关（2026-09-21 追加，规则见 §3.11） | 关 |

全局项不随课表；提醒内容始终按**当前课表**计算——切到哪张表就提醒哪张表的课，无逐课表配置。
作业提醒与上课提醒共用同一闹钟与核对 Worker（取两者中更早的下一个触发点），只有开关、通道、
去重键各自独立——见 §3.11 与 §4.20。

#### 通知口径

- 触发点（2026-09-22 起两个，共用上课提醒开关）：「上课前 N 分钟」（节次开始时间 − 提前量）
  与「上课时刻」各发一条；一节最多两条，各发一次。
- 文案：提前量通知标题「N 分钟后上课 · 课名」；上课时刻通知标题「上课 · 课名」；
  正文「`10:15–11:40` · `@南B208` · 教师」
  复用 `domain/TodayFormat` 的 `metaLine` 口径，不另写。
- 通道（2026-10-05 换 id 迁移）：`class_reminder_v2` / `homework_deadline_v2`，importance HIGH
  （横幅展示，用户可在系统设置降级）+ **渠道带振动**（双震 pattern，与免费时长提醒同节奏）。
  渠道建出来后振动与 importance 都改不动，旧 id（`class_reminder` / `homework_deadline`，
  无振动版）由 `ensureChannels` 删除，迁移挂在冷启动重排上（升级后不用等下一次提醒触发）。
  点击进主界面；自动消失。
- **发出即直接震动**（2026-10-05，`ReminderVibration`，与免费时长提醒同一共享工具；
  **2026-10-06 起收在「通知强提醒」开关后面（入口：我的 → 提醒与桌面 → 提醒；2026-10-07 迁入）**——它穿免打扰，属强打扰，
  默认关，见 §3.3 该节）：
  HyperOS 对第三方应用的通知策略（悬浮通知 / 声音 / 振动 / 锁屏）**默认全关、且不认渠道创建参数**
  ——2026-10-05 实测（Redmi K70 Pro）：渠道记录里 importance HIGH、`mVibrationEnabled=true`，
  设置页那几个开关照样显示关，App 也没有公开 API 能改这个策略层。`Vibrator` 直接震动不走
  通知策略，是「有感」的保底。**悬浮通知只能用户手动开**（系统设置 → 通知 → 水贝贝 →
  对应渠道），提醒设置页已常驻「去系统设置」出口。
- 窗口已过（迟到型补发）**不补**——「10 分钟后上课」在已经上课时发出来是噪音。
- 同一节课的每个触发点只发一次：DataStore 记「已发键」，前缀区分两类
  （`before|日期|课id|起始分钟` / `start|…`），闹钟与周期核对共用去重；
  旧版无前缀单键读路径迁移为 `before|`。

#### 调度（与 §3.6 同构的三层兜底）

| 层 | 机制 | 作用 |
|----|------|------|
| 1 | `AlarmManager.setAlarmClock` 排上课与作业各触发点中**最早**的一个（上课侧 = 提前量点与上课时刻点取更早；可跨天，最多向后找 14 天） | 主路径 |
| 2 | WorkManager 15 分钟周期核对 | 闹钟被 ROM 推迟、重启丢失时补排/补发 |
| 3 | 冷启动 / 课表·学期·作息数据变化 / `BOOT_COMPLETED` / 设置变更 | 立即重排 |

- **用 `setAlarmClock` 而非 `setAndAllowWhileIdle`（2026-09-23 改）**：真机上
  提醒迟到几分钟是反复出现的问题，`setAndAllowWhileIdle` 是非精确闹钟，
  ROM（尤其 MIUI/澎湃OS 的省电策略）可把它推迟；`setAlarmClock` 是系统级精确闹钟
  （系统时钟应用的同款通道），到点即触发、不受 Doze/省电推迟，且**不需要
  SCHEDULE_EXACT_ALARM 等任何特殊权限**——代价仅是触发时状态栏短暂出现闹钟图标，
  对「上课提醒」这个语义反而贴切。小组件刷新（§3.6）保持 `setAndAllowWhileIdle`
  不动：晚几分钟无感知差异，不值得为它常驻闹钟图标。
- 无效场景不排：提醒关、学期未配置、课表为空、不在学期周次内。
- 下一个提醒时刻的计算是纯函数（`domain/ReminderPlanner`，JVM 可测），
  Android 侧（`ui/reminder/`）只负责排闹钟、发通知、去重落盘。
- 「上课时刻」点的补发窗口 = 上课后 15 分钟，越过即跳过（迟到的「开始上课」是噪音）；
  15 分钟窗口是硬编码常量，不进设置项。

### 3.9 共享单车扫码（2026-09-20，P6）

学校共享电单车由第三方小程序运营（扫码开车）。车身二维码 = 一条普通链接的二维码
（`https://www.kvcoogo.com/ebike?id=<车号>`），运营方在小程序后台配了「扫普通链接二维码
打开小程序」规则，**完整 URL（含 id）经 `q` 参数透传给小程序**。因此改 id 生成的二维码
前缀不变、规则照命中，小程序加载对应车辆——App 内输入车号生成二维码，微信一扫即开车。
（可行性 2026-09-20 真机验证；「App 直拉小程序」走不通：开放平台拉起 SDK 需企业主体认证、
URL Link/scheme 需运营方 access_token，本项目个人开发者两条都不满足，二维码是唯一通路。）

**四态同几何（2026-09-26）**：付款码页此前有骨架，但骨架与成品并不等几何——条码占位写死

1. QR 位 `aspectRatio(1f)`（码图 720×720）；

3. 信息行，高度取 `lineHeightDp(bodySmall)`=16dp；加载时这行放加载文案（它本身就是这一行的

原因文字，条码位留空，按钮行给「重试」。文字高度不写死：`lineHeightDp` 从样式的
`lineHeight` 换算（sp → dp 只需乘 `fontScale`，两段换算里的 `density` 抵消），用户调大

### 3.12 权限设置页（2026-09-23，P6）

入口：**我的 → 关于 → 权限设置**（独立二级页，`SubpageScreen.PERMISSION_SETTINGS`）。

把散在各处的权限申请统一成一个子页：忽略电池优化与允许自启动原来只在
桌面小组件设置页（§3.6）里，通知权限申请埋在上课提醒 / 共享单车免费提醒的
开关开启那一瞬（用户不开提醒根本见不到申请框），「锁后台」只存在于自启动的
文案里。2026-09-23 同日补齐：日历读写（课表同步）与
定位（附近单车地图）也进这个子页，加上相册写入（仅 Android 9 及以下需要，
10 起 MediaStore 免权限、整块隐藏）——用户不用再猜「还有哪些权限没给」。

各行结构（每行 = 图标 + 标题 + 一句说明 + 状态徽标 + 动作按钮）：

| 权限 | 检测 | 动作 |
|------|------|------|
| 忽略电池优化 | `PowerManager.isIgnoringBatteryOptimizations` | 直接弹系统确认框；ROM 不支持该 action 时兜底到白名单列表页 |
| 允许自启动 / 锁后台 | 无系统 API（厂商私有），不显示徽标 | 依次尝试小米 / 华为 / OPPO / vivo 的自启动管理页，全部失败兜底应用详情页 |
| 通知权限 | `NotificationManagerCompat.areNotificationsEnabled` | API 33+ 未授权 → 先弹 `POST_NOTIFICATIONS` 申请框；**被拒后立刻跳系统通知设置页**（`AppPermissions.jumpNotificationSettings`，ROM 不认这个 action 时兜底应用详情页）（不在原地重弹：系统第二次起静默拒绝、申请框根本不出现，反复点只会像坏按钮），API 26–32 同样直接跳 |
| 日历读写 | `AppPermissions.calendarGranted`（READ + WRITE 都要） | 未授权先弹申请框，被拒后跳应用详情页 |
| 定位 | `AppPermissions.locationGranted`（精确/粗略**任一**即可）+ `locationServiceEnabled`（系统「位置信息」总开关） | 徽标 = 两个条件**都**成立；权限缺 → 申请框，拒后跳应用详情页；权限在但总开关关 → 文案点出差异（点行跳应用详情页） |
| 相册写入（仅 API ≤ 28 显示） | `AppPermissions.albumWriteGranted` | 未授权先弹申请框，被拒后跳应用详情页；API 29+ 系统不要求该权限，整块不显示 |

检测与跳转的唯一实现在 `ui/common/AppPermissions.kt`：权限清单（`calendar` /
`location` / `albumWrite*`）、`missing` 过滤、定位总开关检查，以及两个系统设置跳转
——「应用详情页」（`jumpAppDetails`）与「应用通知设置页」（`jumpNotificationSettings`，
2026-09-30 从权限设置页搬过来共用，渠道细分 / 横幅 / 震动都在那一页）都在那里，
课表页分享弹层、日历同步页、出码页、单车地图页（快趣设置弹层的「通知与悬浮」）与权限设置页共用
——不再各写一遍
`listOf(READ_CALENDAR).filter { … }`。

状态徽标在 launcher 回调与 ON_RESUME 重读（用户跳系统设置改完回来，徽标跟着变）。
交互口径与 §3.6 相同：**进页只读检测，不主动弹任何系统框**，申请都由用户点「去开启」触发。
申请框只有第一次点「去开启」会出现，之后这条路都直接落到系统通知设置页——
那里是拒绝之后唯一还能把开关打开的地方。

原入口保留：小组件设置页的「后台及时性」两行、提醒开关开启瞬间的通知权限申请
都不删——它们是功能语境里的就近引导，权限设置页是统一出口。跳转逻辑复用
`WidgetCapabilities.jumpBatteryOptimization / jumpAutoStart`，不复制第二份。

### 3.13 生活页（一卡通 · 寝室电费，2026-09-23，P6）

底栏第三项「生活」（课表右侧），把原来散在今日页与「我的 → 校园卡」的一卡通能力
与新的寝室电费收进一页。**开关**：`DisplayPrefs.lifeTabEnabled`，**默认开**，
入口在「我的 → 通用设置 → 页面与导航 → 生活页」；关掉后底栏回到 3 项（在页内关掉时自动退回今日页，
二级页入口不受影响）。**通用设置里的「启动页」也跟着少一项**：生活页关掉时
「生活」不再出现在启动页选项里，已选的那一项落回今日页（§3.3「启动页」）。

页面结构（自上而下，滚动区 16dp 边距、卡片间距 12dp，均走 `AppCard`）：

| 区块 | 内容 | 行为 |
|------|------|------|
| 付款码条 | 图标 + 「付款码」+ 副标题「等同现金，也能刷宿舍门禁」+ 「出示 ›」 | 点击进全屏付款码页 `PAY_CODE`；凭证未开启时整条变「付款码未开启 / 去开启 ›」，落点「我的 → 校园卡」。**本页不内嵌码位**（2026-09-26 收口，见下） |
| 我的钱包卡 | 一张全宽卡，左右两栏：一卡通（正式卡余额 + 「电子账户 ¥X」）、寝室电费（房间号 + 剩余电量 + 「≈ ¥X · 0.62 元/度」）；栏标题行右侧是各自的取数时刻 | 点任一栏刷新那一栏；「充值」开对应弹层，凭证未开启时两栏一起变「— / 未开启凭证」且按钮变「去开启」；卡头状态行承载「有充值正在确认到账…」「正在查询余额…」；卡头圆圈问号弹「钱包说明」（余额说明 + 电费说明两段） |
| 最近流水 | 按来源分两段：「一卡通」「寝室电费」。段标题带底色，右侧各接自己的出口 | 每段至多 2 条（`LifeFeed.SECTION_LIMIT`），空段给一行提示。「一卡通」段右侧进 `CAMPUS_STATEMENT`；「寝室电费」段右侧进 `POWER_BILL`（2026-09-26 起分段，见下） |

**2026-09-26 版式重构**：三处收口，起因是页首那张付款码卡在未取码时要占 QR 空框 1:1 + 条码位
+ 三枚置灰按钮（按 392dp 宽的机器算约 280dp），展示的内容却是「还没有出示」。

- **付款码卡 -> 付款码条**：本页只留一行入口，点了进全屏 `PAY_CODE`。全屏页本来就有 QR、
  Code128、余额、消费流水入口与扣款自动退出，出示这件事放那边比在卡片里挤着看更清楚。
  点击次数没有变多（过去「点占位条 -> 等取码 -> 在卡里看」，现在「点这一条 -> 全屏看」）。
  内嵌用法连同 `CodeSlots` / 取码骨架一起删掉，码位几何的两条旧口径（四态同几何、三枚按钮
  等宽）随之失效。
- **两张半宽卡 -> 一张全宽钱包卡**：各约 160dp 内宽放不下房间号与「≈ ¥34.45 · 0.62 元/度」，
  且为了两卡恒高等外面还搭了一套 `IntrinsicSize.Min` 骨架。合卡后两栏都放得下。
- **「常用」四格拆掉**：两个充值跟着各自的钱包栏走，消费流水与缴费账单跟着流水段走。
  「常用」这层脚手架让用户先在脑子里把「一卡通」和某一格对应上，多一步。

流水**按来源分两段**（`LifeFeed.sections`，替换原来的 `LifeFeed.merge` 混排）：一卡通落
消费流水页、电费落缴费账单页，混在一条列表里挂两个出口，点之前看不出会跳去哪。

**流水区分段先骨架（2026-09-26 补；同日再改分段就绪）**：两个来源都是异步的（一卡通在
Room、电费在缴费平台，而且电费那条串在读数之后才发），第一帧两段都是空的。此前直接按
空态渲染，用户先看到「还没有消费记录 / 还没有电费流水」，数据到了再跳成真流水，报的就是
「寝室电费的流水卡片要等加载再跳出来」。上线后用户又报「最近流水加载太慢」：整卡共用一个
loading 时，就绪等的是两段里最慢的电费（网络往返），本地一卡通明明毫秒级就绪却陪挂骨架。
现在拆成 `LifeUiState.campusFeedLoading` / `powerFeedLoading` 各自从 **true** 起、各自就绪
各自转数据；为 true 的那段渲染两条骨架行（`FeedRowSkeleton`，内边距、图标尺寸与两行文字
高度都跟 `FeedRow` 对齐，高度走 `lineHeightDp`；文字条本身取行盒的 **62%**、在行盒内垂直
居中——实心条按整行行高画，上下两条贴死成一块，2026-09-26 用户反馈「骨架矩形都粘在一起了」；
行盒总高不变，零位移照旧）。条数在拿到数据前未知，真实数据只有一条时
该段会缩一次——预知条数才能做到绝对不动。

两段「就绪」各看各的：一卡通侧看 Room 流首帧；电费侧看流水那条链路跑完一次
（**成功或失败都算**，失败时该段落到空态提示，不会一直挂着骨架），没开凭证时直接算就绪。
不要用 `PowerCardState.loading` 代替——它只管读数那一段，流水与读数并行请求（2026-09-30
起，此前串行）它完全不覆盖，拿它判会不准。

电费段另有一条兜底（2026-09-26 同日晚）：上次成功流水落 `PowerHistoryCache`（filesDir
JSON，§4.24「请求节流」有完整口径），进页先用种子顶上、链路跑完原地替换——冷启动读数链
要串行跑 登录→详情→读表 三条（流水与它并行，2026-09-30 起），此前这段时间电费段只能挂
骨架（用户报「一打开一直是骨架屏，手动一刷新反而秒出」，刷新快是因为那时 token 已经热了）。
骨架因此只在真·首次启动（还没有种子）出现。

**钱包卡的读数同理（2026-09-27）**：电费栏此前是唯一还会从「—／读取中…」起步的地方
（用户报「首次进入生活页电费余额还是很慢，手动下拉就秒出」），而它等的正是这条链路的
前三条。种子的来源不是新文件，而是 Room `power_readings` 最新一条读数——同一份数据、
同一处写入（`PowerRepository.snapshot()`），零网络拼成展示快照顶上：房号取读数里的
`roomName`（`roomId` 是平台数字 id，显示出来是一串数字），单价缺失就不折算、副行写
「上次读数」，读数时刻照实写在栏标题行右侧。卡上已经有数时（真读数、或刷新失败保留的
上次读数）种子一律不填，免得旧值把新值盖回去。

三条口径（改之前先读）：

1. **码不预取**：进页只拉余额、电费与流水，付款码要点了那一条才进全屏页取码
   （`PayCodeScreen` 进页 `load()`）。本页不内嵌码位，窗口里不留付款码；防截屏与亮度拉满
   由全屏页负责（与 §3.10 同口径）。
2. **失败不编数**：电费读失败时保留上次读数与其时刻（`PowerCardState.snapshot` 不清空），
   错误文案单独一行。余额、电费、流水三处各自失败各自提示，互不牵连。
3. **一处凭证**：电费与一卡通共用 `YktCredentialStore` 的学号 + 查询密码
   （2026-09-23 实测两平台同一密码）。因此一卡通关掉（凭证被清除）时，电费卡同样显示
   「未开启凭证」，不会出现「有余额没电量」的半开状态。

**首帧不许按「未开启」渲染（2026-09-24 修「冷启动首次切到生活页整页跳一下」）**：
开关来自 `CampusCardViewModel.enabled`，它是一条 DataStore 流；`stateIn` 的初值就是首帧的
值，而 DataStore 的第一份数据必然晚于首帧。初值原来写 `false`，于是首帧整页按「未开启」
渲染（付款码条矮一截、钱包两栏是「— / 未开启凭证」），真值到达后换成正常版式，下方内容
整体往下跳。Redmi K70 逐帧核验（1080×2400，screenrecord + 抽帧 + 模板匹配）：修前首帧的
「常用」标题在 y=1172、约 0.3 秒后跳到 y=1840，一次位移 **668px（≈243dp）**（量的是旧版式，
数只作量级参考）；修后首帧就在 y=1840，全程不动。口径：`enabled` 的初值取**凭证在不在**
（`hasSavedAccount`）——开启 / 关闭与存 / 清凭证是同一流程里的成对写入（设置页 `enable` /
`disable`、首启引导），所以它是首帧能同步拿到的最准的值；读加密存储在本类 `init` 里本来就
有一次，多这一次读的是同一份内存缓存。**别再把它改回 `false`，也别拆成「`false` + 另一条
ready 门闸」**（两条流不同帧到达，冷启动照样闪一次，同 §3.3 dock 那次教训）。

**刷新只有下拉一个入口（2026-09-24 用户要求「改成软件同款下拉刷新，右上角的刷新去掉」）**：
顶栏那颗刷新图标删掉（顶栏现在只剩「一卡通设置」），改用与消费流水页 / 缴费账单页同一套
`PullToRefreshBox`；今日页是更早的手写版本（自定义 56dp 阈值 + 手放 `PullToRefreshDefaults.Indicator`），
生活页不自定义阈值，用默认件。下拉一次刷三样：电费读数 + 一卡通流水增量同步 + 一卡通余额，
**全部 `force = true`**（用户明确要看最新，不走缓存与 10 分钟闸门，§4.24「请求节流」）。
「点卡片刷新」两处保留——它们各管各的那张卡，下拉是「一次全刷」。

**三路并发、登录只登一次（2026-09-30，用户报「下拉刷新要刷新很久」）**：指示器等的原是两条
**全串行**链的较慢者——电费读数（登录→项目详情→读表）与一卡通余额（安全键盘→OAuth→
`queryCard`→`queryCard?scene=recharge`）——冷 token 时各自还要先登一次。收口成三处并行/去重：
① `LifeViewModel.refreshPower` 电费流水与读数**并行**（原先串在读表之后）；②
`CampusCardViewModel.fetchBalance` 正式卡与电子账户两问**并行**；③ `YktRepository` /
`PowerRepository` 的登录互斥锁内**复用**等锁期间别路登好的 token（并发冷启动两平台各只真登
一次；401 重登传 `staleToken`，只挡刚试废的那个）。指示器口径不变：等「读数链」与「余额链」
较慢者归零 + 650ms 最短驻留；流水两条不挡指示器。**公开的 `login` / `loginForToken` 仍是
强制真登录**（设置页「保存并开启」要验用户现输的密码，别给它加复用）。

两个细节（都照今日页的口径，改之前先读）：

1. **padding 收在刷新容器上**，不要把 `padding.calculateTopPadding()` 留在滚动区里：
   Scaffold 的内容从 (0,0) 铺满整屏、TopAppBar 压在它上面，指示器挂在容器顶边时整条滑入
   轨迹都在顶栏后面，得拖过阈值一大截才露出半圈，读起来是「拉了半天没反应」。
2. **`isRefreshing` 只认下拉这个动作**（`manualRefreshing`），**不要**写成
   `manualRefreshing || state.power.loading || balanceRefreshing`：进页那次 `refreshPower`
   也会把 loading 置 true，聚合的话一进页就转圈。`manualRefreshing` 靠
   `LaunchedEffect(manualRefreshing, busy)` 撑到各路标志归零，再加 650ms 最短驻留——
   既盖住「onRefresh 回调瞬间标志还没置位」的空档（否则指示器被立刻收回，体感是
   「拉下去又弹回去」），也让网络快时不至于闪一下。

**取数时刻写在栏标题行（2026-09-26）**：两张并排卡时代，时刻与说明挤在 24dp 高的底行里，
说明文案半屏宽放不下、时刻常被省略号吃掉（2026-09-24 只好把说明收进圆圈问号图标）。合成
一张全宽卡后，一卡通与电费的取数时刻各自写在**自己那一栏的标题行右侧**：两个数字本来就不
是同时取的，摆在同一行会让人以为是同一时刻的快照。底行与 `CardFooter` 随之取消。

**说明弹窗**：卡头那枚圆圈问号保留（形态不变，`HugeIcons.InformationCircle`，不用感叹号
——2026-09-24 用户反馈「看起来还以为账号有风险」；这里补的是中性说明，不是告警，感叹号只
留给真的出错）。点击弹「钱包说明」，里面是原来那两段文案各占一段（余额说明 / 电费说明）。
图标自占一格并**吃掉自己那块点击**，不会连带触发整栏的刷新——栏内 `clickable` 收不到已被
子级消费的事件。

**两栏等高与按钮对齐**：Row 走 `height(IntrinsicSize.Min)`，两栏各 `weight(1f)` +
`fillMaxHeight()`；栏内在副行与「充值」之间放一个 `weight(1f)` 弹性空隙，内容高的那一栏
撑开卡片，矮的那栏把多出来的高度堆进空隙，两个「充值」按钮落在同一水平线。

`contentPadding`。M3 的 `ButtonDefaults.MinHeight` 是 40dp，但 `defaultMinSize` 只在传入
约束的 min 为 0 时才顶上去，显式 `height` 给的是死约束，所以 32dp 生效。

**充值到账的返回提醒（2026-09-24 补）**：生活页与「我的 → 校园卡」共用 `CampusCardViewModel`
的到账状态机。生活页此前只挂了「到账成功」弹窗，从微信返回时既不补检也没有「正在确认」
反馈（用户报「生活页充值后没有返回软件的弹窗提醒」）。现在本页与设置页同口径：进/回前台

2026-10-07 起该弹窗与「充值成功」弹窗都以金额大字 `AmountHeroText` 为主，说明文案退为小字）；
两张弹窗互斥——到账那一刻 `markArrived` 先把确认弹窗撤下。弹窗关闭不影响后台轮询，

**用电统计**（2026-09-24，用户要的「按天/周/月的电费使用」）

平台**没有**用电量接口（2026-09-24 逐个试过 H5 bundle 里的统计类接口：
`/turnover/mouthAccount` 是一卡通月消费、`/turnover/app_totalAccount` 是累计缴费、
`/turnover/appAccountDetail` 直接 500），只有「当前剩余电量」这一个读数。
所以用电量靠**本机记录读数 + 相邻差分**推算。

| 项 | 规格 |
|----|------|
| 记录时机 | `PowerRepository.snapshot()` 真打了一次平台拿到新读数时落库（`power_readings` 表，§4.24）。三处覆盖：生活页进页/刷新、账单页下拉刷新、余额提醒的每日核对。**不做后台轮询**——第三方平台，记录密度就等于用户打开 App 的密度 |
| 公式 | 一段用量 = 上次度数 + 段内充值度数 − 这次度数；充值度数 = 充值金额 ÷ 单价（电表是靠充值加电的，不扣掉它，充过值的那段会算成「没用过电」） |
| 算不出的段 | 单价未知又段内有充值 → 跳过；读数涨得比已知充值能解释的还多（流水未取到 / 平台登记延迟 / 电表改数）→ 跳过。**不按 0 记、也不记负数**，只在页面上报「有 N 段对不上」 |
| 跨天归属 | 两条读数之间按**时间占比均摊**到各自然日，再按日汇总成周（周一起）与月。读数密时（进页就记一条）接近真实，读数疏时按天看到的是均摊值——页面里如实说明 |
| 窗口与档位 | 日（近 14 天）/ 周（近 12 周）/ 月（近 12 个月），切档本地重算、零网络；空桶补零 |
| 页头 | 剩余电量 + 折算金额（`BalanceAlert.remainingYuan`，单价缺失就不给金额）+ 最近读数时刻 + 档位分段控件 + 窗口合计（度 / ≈ 元 / 期间充值）+ 柱状（`AppBarChart`，**柱子可点**；选中的桶在标题行右侧显示「标签 · N 度 · ≈ ¥X」，2026-09-26） |
| 列表 | 有量的桶逐条**装进一张卡**（行间细线）：标签（今天 / 昨天 / `09-24` / 本周 / `9/14 起` / 本月 / `2026 年 8 月`）· 度数 · ≈ 金额 · 充值小注（有充值的桶才显示）；柱状图选中的那一行带一层浅底，柱与行对得上 |
| 房间 | 统计只看**最新那条读数**的房间：换寝室后曲线从新房间重新开始，旧房间的记录留着但不参与 |
| 空态 | 没有读数 / 只有一条读数时给「读数怎么来的、怎么才有曲线」，不显示一行「暂无数据」 |

落位：`domain/PowerUsage.kt`（差分、均摊、桶与标签，纯函数，`PowerUsageTest` 覆盖）、

`PowerRepository`），但共用同一份凭证与同一个付款码状态机（`PayCodeViewModel`）。
充值弹层（`RechargeSheet`/`PowerRechargeSheet`）与快捷方式表单弹层统一走
**`ui/common/SheetDismissIme.kt` 的 `ImeAwareModalBottomSheet`**（键盘遮挡 + 退场时序一份口径；
它内部钉死 `skipPartiallyExpanded = true`）。跳过该锚点的根因（2026-09-24 真机定位）：
键盘弹起让弹层可用高度从 2400px 掉到 1604px，986px 高的内容就满足 M3 的「高于可用高度
一半」条件，于是 M3 造出 `PartiallyExpanded = fullHeight/2` 锚点，并在锚点更新时把 target
从 Expanded **改判**成 PartiallyExpanded → 弹层停在 802px 而不是 Expanded 的 618px，
差 184px 正好把最底部的「下一步」压进键盘（用户手动上划 = 拖回 Expanded，所以「划一下
才看得见」）。跳过该锚点后只剩 Hidden/Expanded，键盘弹起时 target 保持 Expanded（实测
618px，按钮落在键盘上缘之上）。**内容固定不可滚**（用户拍板，弃用「可滚 + 键盘起来滚到
底」——首次点击时 maxValue 未更新会滚不到位）；**也不要自己垫键盘高度**——M3 已经用
`Box(fillMaxSize().imePadding())` + `contentWindowInsets = safeDrawing.only(Bottom)` 把弹层
底边与内容底垫到键盘上缘，多垫一份会把内容挤出可视区（旧 `ui/common/ImeSheetGuard.kt`
的误诊，已删）。

**退场与键盘必须分两段，不能并行**（2026-09-24 两次修订；用户先报「先键盘退出再弹窗退出、
还有延迟」，改并行后又报「点弹窗其余地方 → 先键盘收回、弹窗延迟收回、收回动画诡异」）。
并行错在：M3 的退场是一条 `tween(300ms, FastOutSlowIn)`（`BottomSheetAnimationSpec`），而
锚点 Expanded/Hidden 由**容器高度**算出（父 Box 是 `fillMaxSize().imePadding()`，键盘一收
1604px → 2400px）——并行收键盘时键盘动画每帧改一次容器高度 → 每帧 `updateAnchors()` →
动画进行中的 `updateAnchors` 会**取消并重启**这条 tween（foundation `restartable{}`），
而时长型 spec 每次重启都从缓动曲线 0 点重新计时、不吸收初速度，终点又每帧往下跑 → 弹层在
键盘收起的整段里每帧只推进剩余距离的不到 1%（`FastOutSlowIn` 在 16ms 处 ≈0.7%），等键盘
收完才把剩下 1500+ 像素用一条 tween 一口气滑完。现在的口径：`confirmValueChange`（M3 自己
询问「能不能去 Hidden」的钩子，点遮罩的 `animateToDismiss` 与下滑松手的 `settle` 都先问它）
在键盘还起着时**否决**这次 Hidden，改由弹层内容里的宿主跑序列——①交还焦点 + 收键盘（弹层
跟着键盘逐帧下移，即 `trySnapTo(Expanded)` 的吸附，就是用户认可的「键盘和弹窗一起跟随收回」）；
②`WindowInsets.ime` 归零（逐帧回调，收到 0 = 键盘动画结束）再 `hide()`：锚点不再变，300ms
tween 一次跑完。两段之间没有空档，超时 450ms 兜底（只防「键盘收不动」时把弹层卡住不退）。
宿主 composable **必须组合在弹层内容里**——写在 `ModalBottomSheet { … }` 外面拿到的是
Activity 窗口的 `LocalFocusManager` / `LocalSoftwareKeyboardController` / insets，收不动
弹窗里的键盘（第一版就这么写错，实测无效）；`ImeAwareModalBottomSheet` 已内建，新弹层直接用它。
