# 收件箱

作用域：改收件箱的数据层、投递挂点或收件箱页时读。规格见 DESIGN §3.24 / §4.38。

## 收件箱是旁路，不反向打断业务链

- 投递只发生在各业务链「数据已到手并完成对比」的结果点上（`ExamSync` 落快照后 /
  `ScoreSync` 写库后 / `ScheduleSync.check` 落待处置缓存处 / `SelectionAlertReminder`
  发通知成功处 / `BalanceAlertReminder` 判定处）。**收件箱链路自己不发任何网络请求**；
  `InboxRepository` 的每个写操作内部吞错只留日志——留痕失败不能让主链路跟着失败。
- 去重语义三条（`domain/InboxRules`，`InboxRulesTest` 钉住）：无键插入；未删重投刷新并
  **重新置未读**（状态型「已读后次日仍低 → 重新未读」靠它）；**已删重投只刷新不复活**。
  消息键见 `domain/InboxKeys`，调课与轮次的键必须与既有指纹/已发键**同源**，别另写一套。
- 保留策略：软删 30 天 / 已读 90 天 / 未删总量 200 条保最新，冷启动 purge 一次。
  `planPurge` 的总量上限**只数未删行**（与列表查询的 `deletedAt IS NULL` 同口径）——
  把软删行计入容量会误裁活消息（2026-10-06 单测抓过这个 bug）。
- 状态消解（余额回升 → 整条移除）只在「成功取到数据且不再偏低」的路径上调
  `clearState`；取数失败绝不误删（同「失败不落日期」纪律）。
- `ScoreSync` 的 changes **恒计算**（2026-10-06 与 `scoreAlertEnabled` 解耦，纯内存比对
  零成本）；通知层自己判开关（`ScoreAlertReminder.check` 里 `if (scoreOn)`），别把
  `alertOn` 判断加回 sync 里——那会连累收件箱丢出分事实。
- 范围边界：时刻型提醒（上课/作业/洗衣/免费时长/抢课）**不入箱**（过期即无用）；
  教务公告没有抓取链路，不收。接新来源时先回答「这条消息三个月后还有回查价值吗」。
- route 存 `SubpageScreen` 枚举名，页面按名安全解析、认不出就不跳；给消息带
  `focusItemId` 前先确认目标页真的消费它。

## 通知总开关只拦「发通知」，不拦核对与入箱（2026-10-06 修正）

- `ScoreAlertReminder.check` / `BalanceAlertReminder.check` 的入口**不许**用
  `areNotificationsEnabled()` 早退——那会把「通知全关」变成「连核对都不跑」，收件箱
  跟着失效，而这批用户恰恰最依赖收件箱。通知开关只拦 `post...` 那一个动作，
  `notificationsEnabled` 作为参数传进各 check 路径。
- 选课链的已发键在「通知真发出」**或**「通知被系统整体关闭」时都落：后者事实已进
  收件箱，重试没有意义；不落键则 `scheduleNext` 会把这个已过去的提醒点反复排成
  立即触发的闹钟，空转循环。只有「通知开着但发送异常」才留给下一轮（同作业提醒）。

## 时间分段

- 收件箱列表按「今天 / 昨天 / 本周 / 更早」分段（`InboxRules.timeGroupOf`，纯 JVM 可测，
  测试在 `InboxRulesTest`）。**判定只用本地时区日期**：本周 = 今天的 ISO 周一起算，
  昨天之前但不在本周的日期（如上周日）归「更早」——按「距今 N 天」分桶会让周日看
  「上周六（6 天前）」进本周，口径漂。页面层逐条与上一条比桶、换桶插头，不额外建
  数据结构；消息删除走整流刷新，分段头不需要位移动画。
