# 收件箱

作用域：改收件箱的数据层、投递挂点、今日页收件箱列表或收件箱页时读。规格见 DESIGN §3.24 / §4.38。

## 入口只有一处（2026-10-21 收口）

- **今日页收件箱列表**（`ui/today/InboxTodayCard`，2026-10-22 起**不包 `AppCard`**：直接铺在
  页面底色上，标题行 + 发丝线分隔的行）是唯一展示入口：常驻（今天没消息也渲染
  单行空态），只列**今天**的消息（按 `timeGroupOf` 的 TODAY 桶本地日期过滤），标题行
  「查看更多」进收件箱页（完整列表 + 一键已读 + 多选删除）。空态页（未开学 / 课表为空）
  贴底也挂——余额预警这类消息不依赖学期。
  **别把 `AppCard` 包回来**：用户口径「列表式，不包裹在气泡里」。
- **宿舍报修状态行**是列表内置顶行（消息行之上）：渲染 `DormRepairRules.cardRecord`
  （在途优先 / 3 天内完成），点行进 `DORM_REPAIR`。**在途状态不写 `inbox_messages`**、
  不进「今日 N 条」计数——收件箱只收「发生过的事实」，在途是随时刷新的当前态；渲染层
  直接消费 `DormRepairStore.snapshot`。别把办结消息（`DORM_REPAIR` kind）和在途状态行
  混为一谈：前者是事实留痕（同键去重），后者是状态展示（快照驱动）。
- 顶栏「+」整套（2026-10-22 删除）、「+」图标本体的未读红点、左侧栏「工具」段的行都已删，
  别再加回去；
  来源图标统一在 `ui/inbox/InboxKindIcon.kt` 的 `inboxKindIcon`（卡与页共用，勿另写）。

## 收件箱是旁路，不反向打断业务链

- 投递只发生在各业务链「数据已到手并完成对比」的结果点上（`ExamSync` 落快照后 /
  `ScoreSync` 写库后 / `ScheduleSync.check` 落待处置缓存处 / `SelectionAlertReminder`
  发通知成功处 / `BalanceAlertReminder` 判定处 / `DormRepairSync` 对比出
  「上次未结束 → 这次结束」处）。**收件箱链路自己不发任何网络请求**；
  `InboxRepository` 的每个写操作内部吞错只留日志——留痕失败不能让主链路跟着失败。
- 去重语义三条（`domain/InboxRules`，`InboxRulesTest` 钉住）：无键插入；未删重投刷新并
  **重新置未读**（状态型「已读后次日仍低 → 重新未读」靠它）；**已删重投只刷新不复活**。
  消息键见 `domain/InboxKeys`，调课与轮次的键必须与既有指纹/已发键**同源**，别另写一套。
- **宿舍报修办结**（§4.49）：`InboxKind.DORM_REPAIR`，key `repair|done|<formUserId>`，
  按**单条报修**去重；只有「上次同一条未结束 → 这次结束」才投递，首跑只建基线。
  完成时间超过 3 天的仍入箱（可回查）但不发通知；route = `DORM_REPAIR`，
  focusItemId = 记录 id。通知渠道 / id 见 `DormRepairReminder`。
- 保留策略：软删 30 天 / 已读 90 天 / 未删总量 200 条保最新，冷启动 purge 一次。
  `planPurge` 的总量上限**只数未删行**（与列表查询的 `deletedAt IS NULL` 同口径）——
  把软删行计入容量会误裁活消息（2026-10-06 单测抓过这个 bug）。
- 状态消解（余额回升 → 整条移除）只在「成功取到数据且不再偏低」的路径上调
  `clearState`；取数失败绝不误删（同「失败不落日期」纪律）。
- `ScoreSync` 的 changes **恒计算**（2026-10-06 与 `scoreAlertEnabled` 解耦，纯内存比对
  零成本）；通知层自己判开关（`ScoreAlertReminder.check` 里 `if (scoreOn)`），别把
  `alertOn` 判断加回 sync 里——那会连累收件箱丢出分事实。
- 范围边界：时刻型提醒（上课/作业/洗衣/免费时长）**不入箱**（过期即无用）；
  教务公告没有抓取链路，不收。接新来源时先回答「这条消息三个月后还有回查价值吗」。
- **账单类静默留痕**（2026-10-21）：快趣骑行结算 / 胖乖开水 / 趣智用水 / U净 洗衣完成四类
  `post(..., silent = true)`——插入即已读、静默重投（`refreshSilent`）保持已读，**不产生未读红点**；
  它们是可回查的流水，不是待办（红点只属于待办类）。**今日卡标题「今日 N 条」数今天全部消息**
  （2026-10-21 二次修正：只数待办类会出现「今日 1 条」却铺着 5 行的矛盾，数字必须和列表对得上）。
  落点：快趣 → `KVCX`（本机骑行记录），胖乖 → `WATER`，趣智 → `QZXY`，
  U净 → `UJING_HISTORY`（历史账单）。
- 今日页收件箱列表固定铺 **3 行**（`TODAY_PREVIEW_LIMIT`，2026-10-21 用户口径），
  **报修状态行占其中 1 行**（有报修时消息槽 = 2），余量一行「还有 N 条」进收件箱页；
  选预览时**待办类优先占位**、账单补足（纯时间截断会让一串流水把带红点的消息挤进「还有 N 条」）。
- route 存 `SubpageScreen` 枚举名，页面按名安全解析、认不出就不跳；给消息带
  `focusItemId` 前先确认目标页真的消费它。

## 通知总开关只拦「发通知」，不拦核对与入箱（2026-10-06 修正）

- `ScoreAlertReminder.check` / `BalanceAlertReminder.check` 的入口**不许**用
  `areNotificationsEnabled()` 早退——那会把「通知全关」变成「连核对都不跑」，收件箱
  跟着失效，而这批用户恰恰最依赖收件箱。通知开关只拦 `post...` 那一个动作，
  `notificationsEnabled` 作为参数传进各 check 路径。
- 选课链的已发键在「通知真发出」**或**「通知被系统整体关闭」时都落：后者事实已进
  收件箱，重试没有意义；不落键则 `scheduleNext` 会把这个已过去的提醒点反复排成
  立即触发的闹钟，空转循环。只有「通知开着但发送异常」才留给下一轮（同作业提醒）。

## 时间分段

- 收件箱列表按「今天 / 昨天 / 本周 / 更早」分段（`InboxRules.timeGroupOf`，纯 JVM 可测，
  测试在 `InboxRulesTest`）。**判定只用本地时区日期**：本周 = 今天的 ISO 周一起算，
  昨天之前但不在本周的日期（如上周日）归「更早」——按「距今 N 天」分桶会让周日看
  「上周六（6 天前）」进本周，口径漂。页面层逐条与上一条比桶、换桶插头，不额外建
  数据结构；消息删除走整流刷新，分段头不需要位移动画。
- 今日页收件箱列表同用这只桶过滤「今天」：先转本地 `LocalDate` 再比，**不要**按
  「距今 24 小时」过滤——23:59 入箱的消息次日 0:01 看就不该再出现在今日卡上。
